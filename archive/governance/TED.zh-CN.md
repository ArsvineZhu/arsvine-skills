# Token 经济开发（TED）

保留所需语义。最小化工程活动的总 Token 成本。

## 1. 总则

工程决策应当在不损害正确性、所需语义、安全性与可维护性的前提下，优化实现、验证、审查、维护以及后续变更所产生的总 Token 成本。

**Token 成本**包括模型上下文、推理、生成输出、重复阅读、重复验证输出、返工，以及当前设计给未来 Agent 带来的额外工作。

即时简短不是目标。当现在投入更多 Token 能够可靠地消除未来更大的重复 Token 消耗时，该投入具有正当性。

规模、抽象程度、泛化程度、依赖数量、文件数量、包数量、流程数量，以及是否存在即时消费者，均不得被视为工程过度的替代指标。

## 2. 有理由的扩展

当工程扩展能够以预期收益抵消并超过新增的实现与推理成本时，可以进行扩展。此类收益包括减少重复工作、歧义、错误或维护负担。

当一个较大的抽象能够为较大的责任提供单一且一致的所有者、消除重复推理、隔离易变机制、保留既定边界，或显著简化已批准的后续开发时，它可以优于多个局部机制。

不得仅因某个实现更小，就优先选择最小实现。

已经确立的开发方向可以在首个消费者出现之前，为相关结构提供正当性。仅仅因为“未来可能有用”，不足以为实质性机制提供正当性。

除非相应流程本身具有独立的 Token 经济价值，否则不得仅因本规则而额外要求论证文档、矩阵、门禁、评审阶段或审批仪式。

## 3. 复用与自动化

对于通用机制，在不放弃所需语义或权威边界的前提下，应当优先使用能够降低总 Token 成本的现有语义所有者、项目原语、标准库、运行时、操作系统能力、协议实现或合适的成熟库。

项目拥有产品语义，并不意味着项目必须重新实现通用基础设施。

依赖数量不是质量指标。

当低成本的成熟工具能够持续减少手工操作、重复推理、格式漂移、可避免缺陷、验证噪声或重复命令，且其持续收益超过配置与维护成本时，应当主动采用。

不得仅为了避免增加工具而保留手工工作。

## 4. 架构与连续性

已批准的抽象和语义边界，应当依据已批准的发展方向整体评估，不得仅依据当前任务评估。

缺少即时消费者，不构成删除理由。

不得仅因当前任务可以使用更少文件或更少间接层完成，就在局部实现中压平、复制、绕过或局部化既定抽象。

现有代码和架构没有自动保留特权。当正确性、语义、已批准的演进、维护负担或 Token 成本证明变更具有正当性时，可以重写。

开发历史本身不产生兼容义务。兼容机制必须对应真实存在的当前义务。

历史故障可以成为永久自动化或防护机制的证据，但前提是其暴露的风险仍然存在，且预期的持续收益足以证明维护成本合理。历史是证据，不是自动产生约束的权威。

## 5. 流程纪律

开发流程属于工程机制，应当与代码接受相同的 Token 经济标准。

计划、ADR、门禁、矩阵、资格体系、强制 TDD 阶段、评审阶段、证据包、检查清单、稳定化阶段和关闭流程，只有在其减少的持续不确定性、协调成本、风险或返工超过其自身带来的成本时，才应当存在。

组织惯例、专业外观和流程完整性本身，不构成独立的流程理由。

单次事件不得自动转化为永久仪式。

## 6. 失败处理与测试

失败处理应当与系统实际需要承担的保证和风险相匹配。

重启、重试、重置、人工介入、显式失败或更强的恢复机制，均可能是正确方案。不得仅因还能想象出另一种失败，就继续增加恢复层级。

测试应当保护有意义的契约、已观测风险或具有信息价值的不确定性。

TDD 是可选技术。不得仅为了证明尚未编写的功能不存在，而创建失败测试。

不得仅为了测试便利而创建生产架构。

## 7. 验证经济性

验证应当在保持所需置信度的前提下，最小化时间、计算资源、上下文污染和 Agent 的重复阅读。

迭代期间，应当运行能够证伪当前变更的最窄检查。除非相关失败无法在更窄边界上评估，否则不得在每次小修改后重新运行完整验证套件。

当广泛验证暴露出范围明确的失败时，应当一起检查相关失败，在最有用的窄范围内修复，并在有意义的集成或验收边界再返回全面验证。

反复缓慢、嘈杂、冗余或作用域不当的验证，本身就是工程问题。

验证工具属于普通工程。只要在运行时间、计算成本、Token 成本、诊断精度或失败定位方面的预期持续收益超过其维护负担，就可以重构、扩展或新建验证工具。

当现有工具能力足够时，应当使用现有能力；当其不足且预期净收益为正时，可以使用定制工具。

验证输出应当优先采用简洁、确定性、非交互式的诊断。应在可行时移除不必要的 ANSI 颜色、进度动画、监视模式噪声、重复堆栈、重复失败信息和冗余成功输出。应优先呈现有用诊断，并在需要时单独保留完整日志。

## 8. 执行权限

Executor 应当实现已经决定的语义、所有权、边界、提供者选择、兼容义务、安全约束和失败策略，同时保留正常的实现判断权。

遇到重大的未决问题时，应当升级处理。不得通过新增抽象、配置项、注册表、回退、策略层或通用框架来掩盖该问题。

已批准的能力应当完整实现。不得以 Token 经济为理由削弱需求或交付不完整行为。

## 9. 写作经济性

文档和面向用户的文本，应当在保证清晰与准确的前提下，用最少的文字传达所需含义。

写作者不得把“先构造一个可能的误解，再进行否定”作为默认表达结构。

“不是 X，而是 Y”“这并不意味着”等否定式对比，只有在该区别会实质影响理解时才应当使用。

主要界面文案应当服务于用户当前任务。内部来源防御、方法论自我辩护、实现细节免责声明以及预防式反驳，不得进入主要文案，除非它们会实质影响安全、操作或结果解释。

相关限制、不确定性和来源信息应当直接、一次性地表达，并放在最窄且合适的信息层级。

“简洁”应当意味着删除重复与无关内容，而不是删除正确理解规则所必需的信息。

## 10. Token 经济测试

在新增、扩展、保留或删除任何非平凡的代码结构、抽象、依赖、工具、测试、验证机制、文档、门禁、工作流或流程之前，应当问：

> 该决策是否能够在不损害所需语义、正确性、安全性和可维护性的前提下，降低已批准开发方向上的预期总 Token 成本？

如果答案为是，则允许该决策，并应当以与其责任相称的范围实施。

如果答案为否，则不得仅因为某项机制显得完整、专业、可扩展、防御性强、符合惯例或理论上可复用，就新增或保留它。

“相称”不等于更小、更少、更少抽象或立即被消费。其含义是：预期的持续价值足以证明持续的推理与维护负担合理。

## 11. 完成条件

当已授权行为和所需证明完成后，停止。

进一步工作必须由新的缺陷、需求、已接受的改进或明确授权触发。
