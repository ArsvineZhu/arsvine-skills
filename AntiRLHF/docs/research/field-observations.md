# 问题与现场观察：从软件屎山到漂亮的认错

这些记录来自长期使用 Chat、Research Agent、Coding Agent 的开发实践。它们不是统计抽样，也不是在同一实验环境下得到的比较结果。记录具体故障，是为了提取能改变模型下一步行为的共性问题。

## 局部通过，整体失效

我们看到一种反复出现的开发轨迹：Agent 写一段代码，补一段测试；测试通过后继续添加代码和测试。局部接口被覆盖得越来越完整，最终交付的软件却可能无法启动，使用路径缺失，或不能完成已经提出的能力。

在一次大型仓库治理中，要求是大幅精简代码、拆除重复通用机制、清理测试和复杂流程。执行结果曾出现删除约两万行、却又新增约两万五千行的情况。大量旧测试仍被保留，新结构继续追加测试。Agent 最终报告目标没有达成。数字是具体开发经历，不是对任意模型的总体测量。

这里的失误并非简单的“没有删够”。模型倾向于先问每个旧测试有什么理由保留；几乎每个测试都能被赋予一个听起来合理的作用。于是逐项审查自然导向保留。真正适合大重构的工作单位，是**目标架构所需的验证责任**：先设计新的检查结构，再从旧套件转移必要场景，成组移除被取代的测试和附属机制。

## 兼容、包装与形状固化

另一个典型轨迹是在已有模块上不断附加别名、适配器、回退分支和保留旧接口的过渡层。即使没有现实中的外部兼容义务，模型也会用“减少改动”“不破坏现有测试”来解释为什么旧路径必须活着。

这使系统不断为自己的历史付费。真正有效的抽象可能需要重新设计数据形状、统一语义所有者、迁移调用方，并删除旧结构。小 diff 未必是小成本；所谓谨慎往往让将来的修改更难。

## 删除以后留下“墓碑”

纠正文档时，我们见过模型把被删除的错误转换为否定式纪念品。例如，正确的菜名本应直接写作“番茄炒鸡蛋”，却被改成“番茄炒鸡蛋（没有红烧牛肉）”。随后 Agent 甚至可能在 AGENTS 中加一条关于这次错误的长期禁令。

这不是一个普通措辞瑕疵。**模型没有让已经失效的信息退出当前系统**，而是把改正过程变成了新的长期内容。软件中废弃的适配层、文档中“此处不再……”的注释，以及会议或报告里反复声明“已避免上次的问题”，都具有相似的历史残留模式。

## 局部要求变成全局焦虑

例如，开发过程中要求保持某个软件的登录状态，原意是保护已有授权数据。随后出现一个完全无关的系统错误，Agent 仍主动报告“该错误未影响登录状态”。

局部约束应在其作用范围内安静地生效。它不需要成为所有后续输出的主题，更不需要因为用户强调得很用力而上升为永久项目制度。

## 从语言防御到“认错能力”

<!-- antirlhf: allow rule=logical-limitation-zh reason="Quoted defensive phrases are the research subject" -->
模型常在已经给出足够答案后，继续用“不能证明”“不代表”一类限定，或者先设想用户可能反驳什么，再花文字反驳自己创造的命题。结论由此被淹没，推理得到的确定性也在表达时被削弱。

最值得记录的是后续的纠错：模型受到批评后，往往可以极准确地指出自己违反了哪一条治理原则，甚至分析“事后合理化”本身的缺陷。下一次实际判断却仍然可能重复同一错误。认错文本越精彩，越容易让人误以为行为已经改变。

我们进一步注意到两种独立问题：一是模型对自己为何犯错的解释可能只是当下生成的合理故事；二是“以后我会……”之类承诺缺少未来会话中实际执行的机制。认错可以完成当前对话，却没有生成相应的持续能力。

## 一个共同抽象

这些现象共同指向 **local defensibility optimization**：模型将局部可展示的正确、熟悉的工程步骤、风险说明、测试数量和漂亮的自我反思，当作比用户整体目标更容易优化的反馈对象。

我们关心的下一步，是让治理规则在**最初选择保留还是删除、继续调查还是动手、修改现有结构还是加包装**的时候起效。只在事后引用规则，研究价值很有限。
