# 推理时治理：让原则改变下一项行动

我们当前可使用的干预手段是提示词、Skill、现有工具，以及任务自身产生的反馈。研究目标很具体：在模型**尚未犯错**的时候，它会选择做什么？

## 从“知道规则”转到“选择行动”

一个成熟模型能够复述“没有外部兼容义务的旧接口可以删除”。真正的分歧出现在它看见旧接口还有数个调用者、二十项测试和一堆历史文档的瞬间。

如果 Agent 开始维护旧接口、编写适配器、给新旧路径各补一套测试，那么它仍在依照熟悉的局部安全策略行动。我们要让它选择统一新接口、迁移真实调用者、删除旧路径及其专属测试。这里的**差异必须出现在下一次编辑上**，不需要附上一份说明其如何遵守 Constitution 的报告。

因此，AntiRLHF 在 [Constitution](../../CONSTITUTION.md) 中保留简短的行动原则；在 Plan/Exec Skill 中描述常见分叉时的行动方向；在各自 `references/examples.md` 中放少量完整、跨领域的情境—行动示范。它们承担不同层级的职责，也不要求每次任务都重新朗读。

## 常驻原则、角色知识与任务示范

**Constitution** 常驻，覆盖目标持续性、权威范围、纠错、依据反馈作出选择以及结束工作。抽象规则需要足够稳定，避免把最近一次用户纠正的案例永久刻进所有场景。

**Plan/Exec** 通过 Harness 的 Skill 机制在相关任务加载。Planning 重点处理决策、研究与架构；Execution 重点处理下一次编辑、真实行为、结构替换与验证。两者使用相同的共同原则，但各自选择不同的动作。

**示范**把具体情境连接到可操作的工作过程。写清任务前提、错误发展路径、正确的连续操作，以及条件变化时为什么需要换一种做法。数学任务中的[隐式从错误学习](https://arxiv.org/abs/2502.08550)提供了研究线索；软件仓库中的实际工作仍需按其业务和工程语义设计示范。

案例覆盖真正不同的决策问题。重构和文档 Skill 的参考文章可以充分展开复杂流程；任务不需要的材料由 Skill 按需加载。篇幅由操作知识的完整性决定。

## 什么时候提醒，什么时候保持沉默

[DriftBench](https://arxiv.org/abs/2604.28031) 说明，模型能回忆约束却仍可能偏离。单纯重复整份 Constitution 主要增加规则在文本中的存在感；实际行动能否改变是另一个问题。

在长任务中，`Objective / Decisions / Current Work` 应主要保留仍有效的能力、选择和下一步缺口。例如：

```text
Objective: Consolidate the canonical data owner and complete all active consumers.
Decisions: Old internal shapes may be replaced; no external compatibility obligation.
Current Work: Three consumers migrated. Move the final consumer, then delete the old path.
```

这段状态直接影响下一项操作。命令历史、完整日志和闭合的猜测只在决定下一步仍需要时才保留。

[Remember When It Matters](https://arxiv.org/abs/2607.08716) 将长期状态的价值与选择性介入时机联系起来。其方案有独立记忆 Agent；我们目前先利用现有 Session/compaction 与 Skill 触发机制，在进入重要设计分叉或恢复被中断任务时呈现相关状态，不另建后台监督系统。

## 改变验证的用途

好的检查会改变下一步编辑或证明一个现实依赖的行为已完成。坏的检查只提高“已经很严谨”的感觉。特别是 Agent 自己刚生成的测试，本身可能偏向当前实现，不宜成为系统完整性的唯一依据。

因此，局部测试通过后继续处理尚缺的产品能力；集成路径失败后根据实际错误修正设计；大重构时先重建验证责任，再整体迁移有价值的旧用例。记录实际命令与结果的粒度，服务于协作和排错即可。

对于语言中可以稳定识别的防御句式，保留 `documentation` Skill 的确定性扫描器。它在文本写好后识别错误，不额外要求模型每一句都自我解释。分级规则减少误杀真正有用的技术区别。

## 避免把治理写成新的工作流

我们不要求每个工具调用前填写“规则引用”，不设置周期性自我反省轮次，不要求每个 Skill 生成行为 Eval，也不通过更多子代理向主 Agent 施压。这样的机制需要承担真实的持续收益才值得加入。

同样，不能泛化禁止深入研究、测试、兼容或抽象。任务真的需要较深研究时就研究；持久化数据或外部协议确有兼容义务时就履行。AntiRLHF 的目标是减少无目标的额外工作，同时保留完整且必要的能力。

## 如何区分规则奏效与“说得很好”

如果未来需要检验某条新提示词，可以从已有真实失败记录中恢复一个尚未得到纠正的决策分叉，让 Agent 使用不同指令继续。只看它是否改变了最初的行动选择，以及后续是否完成所需结果。解释文本更顺畅、条款引用更准确，不算完成行动改善。

这种试验只服务于一项真实取舍：某条规则或示范是否值得保留。实际开发体验持续提供后续反馈；没有理由为此建立永久通用评分平台。
