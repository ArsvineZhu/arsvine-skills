# 以正确的作者身份，写给正确的读者

编辑作者原本写的 README、翻译文章、补充研究档案，或给另一个 Agent 编写指令时，读取本文。写作位置应从原文与用户任务确定。

## 维护者的 README 就是维护者在向读者说话

原始 AntiGPT 介绍里有：

> 本文纯手写，在 AI 时代请您珍惜。

这是作者有意选择的表达，既有个人色彩，也带着尖锐和幽默。作者直接对读者讲述一个源于实际模型使用体验的项目。

**错误改写：**

> 本文最初的观察与观点由维护者亲自撰写，后续内容随研究持续修订。

它突然制造出第三方旁白和来源说明，改变语气，额外限定作者身份，回答读者根本没问的问题，还把作者选择表达的意思变了。

**AntiGPT → AntiRLHF 更名时的正确操作：** 保留原句。修改需要变更的项目名、实际能力、链接，以及确实变化的研究范围，沿用作者原有风格和鲜明判断。用户若明确要求改写这句话，再按作者指定语气编辑，不能默认替换为中性的审阅者口吻。

### 修改原文之前

阅读相邻段落，理解它承担的作用：论证、笑话、直接批评、操作指导、解释或过渡。改动技术事实时也要保留原有表达作用。标语可能故意带情绪强度；技术定义可能依赖准确用词。两者都不该随意“润色”成没有个性的统一风格。

不能把作者的第一人称判断转写为某位审阅者的发现，也不要擅自添加解释助手谨慎、严谨或来源审计的尾巴。

## 产品文档、开发文档面对不同读者

**产品使用说明：** 面向想完成操作的用户。“打开设置，选择服务商，保存连接；新服务商会出现在可选列表。”必要前提应真正影响该操作。

**开发者文档：** 面向编写或维护代码的贡献者。“服务商注册表在启动时加载驱动定义。把驱动实现放在 `drivers/`，注册导出的构造器。”这些事实必须来自现行代码。

**研究档案：** 以项目研究者身份记录经历、公开研究和假说，为外部发现提供出处。因果上的未知放在真正讨论因果的段落中，而不是作为 README 开头或宪章中的附带免责。

## 面向 Agent 的文章要直接命令执行者

Skill 的 `description` 属于发现元数据，可客观写：“重构仓库的职责、数据路径、测试和工具，适用于较大结构修改。”

`SKILL.md` 正文、`AGENTS.md` 和 Agent 参考文章是执行指令。直接说明应该操作什么：

| 旁观者口吻 | 直接指令 |
|---|---|
| 防止 Agent 发明新的兼容机制。 | 迁移当前调用方并删除淘汰的内部适配器。 |
| 本技能鼓励谨慎测试。 | 运行覆盖修改行为的检查，针对独立遗漏的故障补充回归。 |
| 该文档可以防止上下文漂移。 | 上下文压缩后恢复 Objective、Decisions 与未完成的 Current Work。 |
| AntiRLHF 旨在改善架构判断。 | 追踪状态修改路径，选择真正拥有修改权的组件。 |

右侧告诉另一个模型能直接执行什么。Skill 哲学目的的介绍，应按读者需求放在 README 或研究档案里。

## 翻译作者作品

保留作者的视角、幽默、确定性、技术术语和表达力度。逐字直译若不自然，可以换自然的表达，但不能趁翻译加入官样限定。原文的引用仍应准确引用。中文原文由作者说话，英文译文也必须由作者说话。

操作 Skill 的译本则保留祈使动作、文件路径和条件。面向中文审阅的版本应准确代表英文指令，使用直接命令或合适的第二人称，而不是从外部讲述“Agent 应当做什么”。

## 以读者身份完成检查

把改后段落当成作者正式发布的文章通读。读者应该直接得到需要的信息、语气和行动，而不是编辑经过。最后运行已有的文档工具，检查受影响链接与语言模式。
