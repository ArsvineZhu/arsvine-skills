# 纠正文案，保留语义，完成修改

修改已有文档、处理语言扫描结果、改正 AI 指令或补救不良编辑时，使用本文。改完的文档应自然呈现为当前版本。

## 在错误原处替换它

**用户指南示例：** 菜名应当是“番茄炒鸡蛋”，现有文档却写“红烧牛肉”。

**错误结果：** “番茄炒鸡蛋（现在没有红烧牛肉）”。错误内容仍永久挂在正确内容后面。

**正确结果：** “番茄炒鸡蛋”。读者只看到现行正确的菜名。删除仅仅解释上次错误的多余句子。

**历史有真正用途时：** 发布记录可以写“2.4 版修正此前错误展示成红烧牛肉的菜名”。历史在发布记录中，而不是永久挂在现行菜单后面。

## 按用户授权修改 AI 指令

**局部纠正：** 用户要求移除 README 某段尾随的无关限定。直接修改该段，并在本次编辑这篇文章时沿用其写作要求。不要在 `AGENTS.md` 加入“永远禁止任何限定”的全局禁令。

**全项目方向：** 用户明确要修改项目的文档规范。编辑有该责任的 `AGENTS.md` 或文档 Skill，保留已有有效规则，以直接动作写出新做法。

**任务期约束：** 用户要求维护期间保留登录状态。任务结束前，涉及该状态的操作都要遵守；在无关报告中不必反复提及。

## 删除凭空出现的反驳与尾随限定

对照用户真正问的问题，以及当前段落已经说清的结论。某一句话如果只用于反驳没人提出的更强命题，就删除它。

**无关尾巴：** “目标运行时的构建已经通过。这不意味着程序在所有可能环境中都能运行。”任务只要求目标运行时的话，后半句没有用处。

**实际区别：** “Windows 构建已通过。用户要求的 Linux 构建仍因原生模块缺失而失败。”这会改变完成情况和下一步动作。

**无关作者来源限定：** “最初由维护者写作，但文档已经经过持续修订。”只有文章真的讨论创作历史时才需要这类信息。

**有用的研究未知：** 真正在论文或研究文章中比较两种机制时，说明哪个观察支持哪个假说、哪些测量能区分它们；无需在段落末尾泛泛宣布严谨。

## 正常处理否定句

`不把`、`不能`、`not`、`does not` 都可能承载关键意思，应判断它们在具体句子里的功能：

- “不要把旧测试原样复制到新架构”是明确的工作指令，确实需要时保留。
- “不把这种结果视为已验证事实”在研究中可能是必要的来源区别，结合它修饰的命题判断。
- “产品已实现本地搜索，不把这说成完整的搜索平台”在发布说明中可能属于凭空添加的限定：读者并没有要求证明“完整搜索平台”。应直接写功能实际提供了什么。
- “未登录时不能调用管理员接口”是有意义的权限限制，保留。

扫描规则应针对反复出现且能够机械识别的表达。依赖语境的模式应引导审阅，而不是强迫删除全部否定句。出现真实误报时调整具体规则，或对教学示例使用范围明确的豁免。

## 保留判断真实达到的确定程度

**弱化的改写：** “我个人比较倾向于采用统一配置服务，不过这当然还有许多值得讨论的方面。”

**有效改写：** “采用统一配置服务。CLI 与 Web UI 通过它修改有效配置，删除各自维护的状态镜像。”

**真实未知：** “迁移完成前，两套持久化数据尚未合并；本次只能启用只读查询。”该事实改变用户能做什么，属于必需内容。

治理目标是保持真实确定性，而不是强制所有回答都语气强硬。

## 先按自然语言审阅，再用现有工具

连贯阅读改后的段落，检查话题、说话位置、作者口吻、自我解释以及句子是否真能帮助读者。扫描器能识别部分重复词形，却发现不了作者声音被第三方取代，也无法辨认所有臆造的反驳。

对受影响维护文案运行扫描器，结合全文处理 `review` 和 `signal`。如果某个坏句式是必要的反例，保留示例并给出针对性豁免；不能直接关闭整条检测。某个精确、可机械识别的问题反复出现时，再改进扫描器。
