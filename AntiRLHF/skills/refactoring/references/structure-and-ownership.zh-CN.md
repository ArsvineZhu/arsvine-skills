# 在真正的所有者层改变架构

实质性的模块、数据模型或内部 API 替换使用本文。追踪真实调用路径，不能仅根据一个现有类名判断所有权。

## 整合之前先追踪实际行为

选择有代表性的操作，沿下列关系查找：

```text
外部入口 -> 输入转换 -> 领域决策 -> 状态修改
         -> 持久化/事件 -> 消费者可观察结果
```

具体系统不一定有外部输入、持久化或事件，只跟踪真实用到的部分。找到规则的决定位置，以及其他模块是否在重复决定相同规则。明确替换影响的消费者，也包括确实存在的配置、动态注册和插件发现路径。

良好的所有权意味着每项职责有明确的权威实现。例如，某组件决定用户有没有权修改记录；驱动负责某外部协议；存储负责持久化写入；UI 负责展示状态。

## 看起来相似的三种情境，解决方案不同

### 同一业务规则被重复实现

**原状：** HTTP、CLI 和内部调度器各自实现 `canPublish(record, actor)`，错误处理也略有不同。修改策略要动三个文件，用户看到不一致的结果。

**修改：** 将 `canPublish` 及策略数据放到拥有发布语义的领域服务。入口负责获取身份、转换规范输入，再调用该服务。删除三个入口各自维护的策略代码。策略测试放在所有者处；真实入口接线可能独立失效时再保留相应检查。

**结果：** 规则修改集中在一个所有者。HTTP 继续负责 HTTP 错误映射，CLI 负责终端输出，调度器负责自己的任务生命周期。

### 不同职责仅共享部分写法

**原状：** 三个适配器解析不同的外部协议，都含有相似的 `decodeHeader` 代码。

**错误整合：** 创造万能 `ProtocolManager`，知道每种外部协议，还负责全部消息分发和每个适配器的错误语义。

**合理整合：** 协议适配器继续独立承担自己的协议职责。真的是同一底层操作、共用 API 又比重复代码简单时，才抽取底层解码函数。成熟 Codec 库有时比自写共享模块更合适。

**结果：** 一个协议改变时，不必同时修改万能管理器或干扰无关集成。

### 相同实体在内部流转为多种模型

**原状：** 路由、存储和 CLI 各自维护同一领域消息的不同可变副本。每经过一个内部边界都要转换字段、同步状态。

**修改：** 让消息服务拥有正式领域表示，存储等消费者使用该契约。数据真正进出外部协议时才转换成协议特有形态。消费者迁移后删除内部镜像与专属转换工具。

**结果：** 消息身份和生命周期只有一个权威定义。传输数据形态仍属于传输边界。无需用 `CanonicalMessageBridge` 再包装原来三套未改变的内部表示。

## 真正的集成边界可以需要适配器

如果外部客户端仍使用公开协议 v1，新客户端使用 v2，那么边界适配器可把 v1 输入转换为当前内部领域模型。明确所承诺的行为与支持期。内部只用当前模型；外部兼容放在入口边界。适配器的依据是真实存在的 v1 客户端，而不是旧内部 API 还有二十项测试。

## 模块与文件组织

按照一起变化的职责及其对外接口组织文件。很大的文件可能混着多个不相关的所有者，可按职责拆分；很多只负责转发调用的小文件也可能形成无谓的间接层。不能把文件行数阈值或固定目录层数当成架构本身。

多个模块共享通用机制时，先看标准库或成熟依赖是否已有合适实现。选择依赖应考察真实 API、维护需要、确实适用的许可证义务和集成成本。它应替换自制工具；对于一个简单纯函数，引入框架可能比保留函数更复杂。

### 目录示例

原状：

```text
src/
  cli-config.ts        # 自行验证配置
  api-config.ts        # 重复验证，默认值还不同
  web-config.ts        # 写入另一份缓存
  convert-config.ts
  convert-config-v2.ts
  config-bridge.ts
```

当三个入口确实使用**同一个配置所有者**时，可能改成：

```text
src/config/
  model.ts             # 正式字段和验证
  service.ts           # 有效状态及修改权
  persistence.ts       # 存储表示
src/cli/config.ts      # 终端输入与输出
src/api/config.ts      # HTTP 边界
src/web/config.ts      # 展示边界
```

具体文件数取决于实际职责。服务本来很小且也负责文件持久化时，可以保留在一个文件里。原转换器与 Bridge 的契约已被所有者吸收后就删除。这里是便于思考的结构示例，不是每个项目都必须照搬的目录模板。

## 将替换完成到消费者

1. 实现已选所有者与契约。
2. 迁移依赖新形态的真实调用方、存储或传输边界。
3. 搜索旧接口和测试专用适配器，删除废弃实现，把有价值的测试转到新所有者。
4. 更新现行开发文档、配置和代码示例。
5. 从受影响入口执行真实操作，解决接线失败。

获准重置架构时，旧内部表示没有仅因已存在就必须保留的权利。真实数据、公开契约和用户无关修改仍有实际的保护要求。
