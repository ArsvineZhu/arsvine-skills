# 重建测试，降低整体维护负担

授权修改涉及大规模架构替换、旧测试让淘汰的内部结构继续存活，或用户要求总代码减少时，使用本文。局部 Bug 修复通常沿用 Exec 的现有测试方法。

## 从目标系统的行为开始

假设某大型仓库有：

```text
tests/legacy-reader/           120 tests
 tests/legacy-writer/          110 tests
 tests/adapter-matrix/         95 tests
 tests/new-storage/            70 tests
 tests/fixtures-and-mocks/     大量专用工厂和 Schema
```

用户要求把两条旧存储路径替换成一个权威存储所有者，保留已有能力并简化整个仓库。

错误做法是打开几百份旧测试，逐条为保留寻找理由。多数测试都能辩护：它覆盖了某个输入、模拟结果或曾经存在的私有调用。这样逐项“谨慎”保留，最终会把旧结构整体留下并额外添加新测试。

应从新系统的**外部行为和能独立失效的职责**开始设计测试，例如：

- 经支持的入口创建、更新、删除和读取。
- 重启恢复与持久化完整性。
- 真正属于契约的权限和持久身份。
- 有意义的事务冲突与故障恢复。
- 值得独立覆盖的复杂解析、算法或状态转换。

具体有哪些契约由系统决定。无需为了凑齐分类而制造测试项。

## 从旧测试找出有价值的场景

旧测试有助于发现边界输入和真实缺陷。查看旧测试组中的代表性案例及历史回归问题。只有新所有者仍可能在相同问题上实质失败时才迁入。例如：

- 缺少可选字段的合法记录，可能需要新模型解析器的一条测试。
- 写入后异常退出与重启恢复，可能需要跨持久化和重启的集成测试。
- 已消失的私有 `LegacyAdapter.getRaw()` Mock 测试，旧适配器删除后没有持续契约。
- 两条依赖不同 Mock 却断言同一规范化行为的测试，可合并为一个数据驱动案例。

目标是保护真实行为，不是把旧断言重新套进新包装器。

## 成组替换测试和配套机制

当新套件已经覆盖对应行为，就删除依赖旧实现的整个测试目录，同时清理只为它们存在的夹具、工厂、Mock 适配器、测试配置和工作流命令。

获授权的内部重写可以同次替换，通常无需为了过渡仪式让两套测试长期并行。实际分批发布或公开兼容承诺可能需要同时检查新旧行为；这种要求来自真实部署方式，而不是旧测试的年龄。

### 测试名称变少，代码仍可能增多

模型把 300 项测试缩为 40 项，却引入通用场景 DSL、多层 Factory、Fixture 转换和新的验证框架。测试数量减少，维护结构反而更庞大。

检查这些新 Helper：多数是否服务于真实重复契约，还是因为新造了框架就必须为它添加配套设施？如果属于后者，使用普通夹具和直接调用重建简单测试结构。

## 保留能够防护独立故障的测试

复杂权限策略的单测，与验证 API 是否实际调用权限检查的集成测试，不一定重复。它们可以独立失败。同理，重启持久化、加密传输、事务回滚，即使都围绕一条存储记录，也可能各有独立故障。

保留真正的独立契约和高代价回归保护。精简针对的是重复证明同一行为及依附于旧设计的机制，而不是实施测试数量配额。

## 与局部修复的对照

**任务：** 修复稳定服务中编码器的一个边界输入。

继续使用原有编码器测试文件，现有检查没有覆盖时补一条简短回归。运行定向测试，契约涉及真实集成时再运行相关集成路径。其他测试结构原样保留。

整体重建设计是为了结构大重构服务。给局部 Bug 修复套用它，只会把预算花在无关测试工程上。

## 施工中始终记住缩减目标

用户要求减少代码时，关注完整变更：生产实现、接口、测试、脚本、生成的胶水代码和工作流设施。Diff 统计可以帮助发现异常增长，但真正的问题是这些新增代码为什么存在、承担什么所需能力。

**例如：** 删除旧子系统 18,000 行，又添加 23,000 行新抽象和测试，最后声称“架构更简单”。此时进入新造的 Bridge、Framework 和测试 Helper，沿真实消费者追踪。如果只是维持旧结构，就迁移消费者并删除。如果承担新增的真正所需能力，就精简周边机制，同时保留该能力。

结束前运行有关真实入口，检查重要契约，更新现行文档并删除旧配套文件。交付时说明实际结构结果，以及它对所需能力和体量目标的影响。
