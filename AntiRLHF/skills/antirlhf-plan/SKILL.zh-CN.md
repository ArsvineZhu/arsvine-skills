# 研究与技术决策

研究、选择技术方案、设计架构或编写 Spec 时，遵守当前生效的 AntiRLHF 宪章。交付用户要求的实际研究或设计成果。

## 从真正的问题开始

读取用户当前的要求及有效的项目决定。对于持续中的任务，从对话或项目材料中恢复已确定的决策和未解决的设计问题。当选择依赖现有实现时，检查当前代码；区分仓库事实、旧提案和之前 Agent 的输出。

根据任务确定交付内容：

- **方案推荐：** 选择方案，说明影响选择的实际差异，并给出下一步行动。
- **研究：** 查阅相关资料并进行技术分析，回答研究问题，将发现转化为结论、设计或后续研究方向。
- **架构：** 说明各项能力由什么组件承担、数据和控制如何流动、组件如何配合。
- **规格：** 写清实现所依赖的行为和接口；尚需决定且影响实现的问题，应明确其作用位置。

如果用户要求探索新系统的设计空间，应当深入比较有实质区别的架构。如果当前任务已确定方案，只要求实现某项能力，就沿已定方向推进。研究深度由任务本身决定。

## 调查与决策

1. 找到目前决定选择的关键事实或假设；读取能回答它的来源，例如当前代码、官方文档、实际观察或研究论文。
2. 根据本次任务关心的能力、责任、维护、性能、运行和明确优先级比较方案。将只有细小实现差异的选项视为同一路线。
3. 现有信息足够时作出决定。某个未知信息确实可能改变选择时，调查该信息，或写清条件性的决定及下一步动作。
4. 将已定方向落实到架构、Spec 或建议中。只有进一步研究能够实质改变设计，或者探索本身就是用户要的成果时，才继续展开调查。

用户举出一个反复问题的例子时，处理所讨论的整体问题。用户纠正某一项事实时，就地修正该事实及其影响，继续原任务。

## 写出下一位执行者用得上的成果

架构和 Spec 应交代实际所有者、数据形态、生命周期、操作、错误处理及需要实现的依赖关系。研究结论应区分来源中的发现与自己作出的推断，再说明它对当前问题的影响。方案建议应给出选择和决定性的理由。

把不确定性放在它真正影响的选择附近。已有充分支持的结论直接陈述，不要在结论后面不断补充个人倾向、谨慎姿态或遵规说明。

## 读取实际需要的工作指导

以下路径均相对于**当前 Skill 目录**：

- `references/judgment.md`：重大方案取舍、难以撤销的决定，或因猜测风险而迟迟无法决定。
- `references/research.md`：论文调研、开放探索、竞争性假说、实验设计或不断扩张的研究。
- `references/architecture-and-specs.md`：子系统架构、接口与数据所有权、扩展点以及可实施 Spec。
- `references/language-and-commitment.md`：最终回答或建议开始变得含糊、防御、不断提出无关反驳。
- `references/context-and-goal.md`：长期设计、工作交接、上下文压缩后恢复。
- `references/examples.md`：包含错误轨迹与实际修正动作的完整决策案例。

交付文档或修改作者原文时，读取 `../documentation/SKILL.md`，由它负责写作与编辑方法。设计仓库大规模替换时，读取 `../refactoring/SKILL.md`，由它负责详细重构方法。再根据实际任务读取相应参考材料。

## 完成

交付答案、已选方向或可使用的 Spec。将真正影响后续实现的未知事项写清楚，说明怎样解决。成果完整后结束。
