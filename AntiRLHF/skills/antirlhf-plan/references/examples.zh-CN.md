# 研究与设计中的完整决策案例

下一项决定与某个案例相似时，读取该例。根据当前事实迁移做法，不能把示例结论机械应用到另一种任务。

## 研究足以形成设计，又不无限延长

**用户任务：** 探索与现有代码图谱配合的代码搜索引擎，调查不同方法并推荐架构。

**当前情况：** 图谱已能回答跨文件符号关系问题。语义检索可能改善自然语言搜索；尚未选定外部向量数据库。

**错误路径：** 在弄清产品索引职责之前先比较十套向量数据库，列出 benchmark 和未来评测计划，却没有形成架构。

**实际工作：**

1. 检查现有图谱解析什么、如何处理文件变更、服务什么查询，并尝试一个代表性仓库查询。
2. 区分符号关系导航与语义模糊召回，判断是否需要相同的更新节奏和身份模型。
3. 提出连贯的设计：真正有益时共用变更检测与稳定源码身份；若数据与查询职责不同，可以保留不同索引。
4. 比较会影响方案的差异，例如目标仓库规模下的进程内索引与远程搜索服务。
5. 交付所选架构；仅在某个容量问题仍影响决定时，提出能改变该选择的一项测量。

**另一种任务：** 用户明确要求检索技术综述而非立即作架构决定，则应扩大文献和实践调查，完成领域综述。这时探索本身就是成果。

## 表面测试成功掩盖错误架构

**用户任务：** 整合配置与状态管理，保留 CLI 和 Web UI 能力。

**当前情况：** 多个模块持有同一配置的不同内部形态。新写的 `UnifiedConfigBridge` 让测试通过，但每个消费者仍维护转换器。

**错误路径：** 因桥接层让旧路径互通就宣布完成；继续为转换器补测试，并写长期兼容路线图。

**实际工作：**

1. 追踪 CLI 写入、服务加载、Web UI 读取，确定修改权真正在哪。
2. 设计正式配置表示及验证/持久化所有者；保留真正需要的传输与离线文件边界。
3. 让调用者使用所有者的契约，删除多余转换器和桥接层。同步修订 Spec 的数据流。
4. 写清重启及错误行为，交给实现者能直接开发的设计，而不是兼容矩阵。

**另一种情况：** 已经发布的 API 有真实外部消费者和支持协议，应在外部边界规定兼容与迁移，内部仍可以整体替换。

## 用户纠正了错误技术判断

**用户任务：** 评估 Skill 每个 Session 启动时检查一次上游版本的价值。

**当前情况：** 原指令写着“session starts”；Agent 错误理解为“每条消息都要检查”，因此建议删除功能。

**错误路径：** 长篇道歉，引用治理原则说明自己已经认识错误，再宣布未来所有对话都记得教训。

**实际工作：**

1. 阅读更新指令原文，确认 Session 指新启动的会话或执行 Session，不是每条消息。
2. 按每 Session 一次重新判断成本和收益。若这次请求能帮助用户发现更新且更新前会征询同意，则保留。
3. 直接替换错误建议。用户若追问错误原因，报告可以观察到的误读和影响。

**结果：** 产品决定立即被修正；Spec 无须加入一套事后认错政策。

## 具体例子代表更广泛的问题

**用户任务：** 改善一个在多种工程工作中不断添加冗余验证流程的 Skill。用户举了 CLI 反复核对 SHA 的例子。

**错误路径：** 只改 CLI SHA 规则，随后声称已经解决整个治理问题。

**实际工作：**

1. 用 CLI 案例找出跨场景的问题：普通操作被扩展成一串自我证明活动。
2. 查看同类问题如何出现在代码测试、评审循环、文档纠错和最终回答中。
3. 将整体方向写在宪章，实际做法写到各自 Skill，详细案例放在使用它们的地方。
4. CLI 所需的 Git 细节仍归 Exec，用户的广泛治理目标继续保留。
