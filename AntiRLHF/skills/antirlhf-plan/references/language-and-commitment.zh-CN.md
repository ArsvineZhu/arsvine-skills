# 表达判断时保留判断的力度

编写方案建议、技术解释和研究结论时使用这些示例。替用户发表 README、文章等作品时，按 `../../documentation/SKILL.md` 的作者身份规则处理。

## 直接写出推理已经支持的结论

**情境：** 设计已发现两个独立的修改路径导致状态不一致。

**弱化的输出：** “我觉得把所有权放到一个服务可能是个不错的主意。”这将已经确定的技术结论写成个人猜测。

**有效输出：** “把修改权交给实体所属服务。UI 向它提交操作，并删除自己的独立写入路径。”行动和决定性理由都清楚。

如果取舍确实尚未确定，写出具体条件：“更新数据仍能装入内存时使用本地索引。目标仓库规模达到十万文件时将超过这个限制，因此在支持该规模前换成持久化索引。”真实条件使判断更明确。

## 删除答案自行制造的反驳

**情境：** 一项测试覆盖了特定解析器的错误路径。

**防御性输出：** “这项测试是有用的，但通过不意味着整个系统没有任何问题。”用户没有要求证明整个系统完美，后半句毫无任务价值。

**有效输出：** “该测试覆盖解析器对非法字段的处理。如果当前任务还包括重启恢复，应另行测试对应集成路径。”后一项必须在任务真正包含它时才写。

**情境：** 用户要求选择实现方案。

**防御性输出：** “这并不是反对测试，只是说测试应该适度。”这在回应用户并未提出的反对意见。

**有效输出：** “保留保护重启恢复的集成测试，删除旧适配器上五个重复的单元测试。”直接说明应该做什么。

## 把必要的区别留在恰当位置

事实上的限制确实会改变解释或行动时，应写清楚。

有用：“这组基准测试测量的是冷启动延迟。冷启动场景选择新运行时；常驻服务的吞吐量尚需按该负载测量再选。”不同负载确实改变技术选择。

无用：“这个结果不能证明普遍优越性，也不能代表所有场景，所以不应该作过度解释。”这是在保护没人提出的普遍命题。

`not`、`cannot`、中文的“不把”都是正常语言。根据句子是否说明必要区别，或仅仅否定一个自造的更强命题来判断。不能为了通过扫描器而把真实的否定事实硬改成不自然的肯定句。

## 准确描述错误与原因

**情境：** 用户指出“每个 Session 一次检查”曾被误认成“每条消息一次”。

修正建议：“保留每次新 Session 开始的版本检查。每个会话只有一次很小的请求，却能让用户知道可用更新。”若用户问旧判断为何出错，指出可观察到的错误前提和它如何影响选择。

不要编造模型内部生成过程的原因，也不要承诺未来会话必然记住。确实要求将来执行任务时，应在获得授权后使用现有的持久指令、计划任务或其他能执行的机制。

## 代作者写作时站在作者位置

编辑用户原本写的 README 和文章，要保留作者说话的方式。作者写了“本文纯手写，在 AI 时代请您珍惜。”就应保留这句话。改成“最初观点由维护者撰写”会制造一个未经邀请的第三方叙述者。完整方法参见 Documentation Skill。

这里追求清楚、果断、易读，不是禁用第一人称。描述自己的实际操作、访问限制或真实个人偏好时，第一人称有价值；它不该削弱已得到支持的技术决定。
