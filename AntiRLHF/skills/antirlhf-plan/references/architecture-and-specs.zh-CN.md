# 架构与可实施规格

选择职责、数据模型、模块边界、插件机制、外部接口，或编写实现 Spec 时使用本文。

## 画组件之前先找出所需行为

沿有代表性的操作，从用户入口追踪到状态变化或外部效果。找出实际实体、谁创建和修改它、保存多久、谁观察结果。现有系统要读实际代码与注册/发现机制；全新设计从需求与批准的发展方向推导能力。

按需用简短流程描述主要行为，例如：

- CLI 修改配置，服务应用新值，重启后状态保持。
- 收到消息后完成规范化、路由和确认，错误行为符合业务要求。
- 用户提交查询，检索引擎找到符号与语义证据，返回可用的排序结果。

由这些流程确定边界。类名、文件布局、架构模式和旧测试只是旧设计的事实，不自动成为新架构的约束。

## 找到真正的所有者，同时避免万能对象

**相同业务规则重复：** 三个入口分别决定消息是否有权限发送。把权限规则及其数据集中给负责发送的领域服务。各入口只负责取得用户身份、转换自己的输入、调用领域服务，以及返回各自协议下的结果。

**不同职责的代码碰巧相似：** 三个适配器要将不同外部协议转换成领域消息。协议职责继续分开；确实通用的序列化基础函数可以共用。把所有协议规则丢进一个 `UniversalDispatcher` 会将无关变化耦合在一起。

**一个实体有多种内部形态：** 服务之间反复转换同一条领域消息，内部还有多个可变副本。应由实体所有者定义一种正式领域表示，消费者使用它。只有真正进出外部协议时才做明确的协议转换；不要再造一个“统一包装器”继续隐藏原有多套表示。

**成熟库候选：** 成熟的解析、消息队列、密码基础组件或存储驱动可以承担已有的通用机制；业务语义仍由本项目负责。引入依赖的结果应更简单，不能仅为了显得架构正规给小函数外面加一个框架。

观察变更时就能看出所有权：领域规则改变应集中修改实际所有者，需要修改契约的消费者则同步迁移。五个模块各改一次相同策略，是所有权分散；一个管理器知道五个模块各自无关的业务逻辑，是过度集中。

## 接口应表达真实边界

确有外部边界、多个具体实现、所有者之间的稳定契约或已批准的扩展方向时，接口有价值。确实动态注册、拥有独立生命周期的组件才需要插件注册机制。只被调用一次的私有函数无需为了“扩展性”包装成插件系统。

使用领域词汇命名操作，明确输入和输出，把可变状态的操作放到选定所有者中。调用者需要处理的错误应有具体语义：重试、事务边界、回滚、冲突、找不到、断线等。公开兼容依据真实消费者和支持承诺。用户允许替换内部结构时，旧内部接口可以跟调用方一起修改。

### 情境：配置管理所有者

**旧系统：** CLI 修改一种 TOML 表示；Server 在数据库写入副本；Web UI 缓存另一份可变对象。三个地方对同一字段分别验证。

**目标：** 选出有修改权限的所有者，由它维护正式领域表示、统一验证和持久化。CLI、Web UI 将操作提交给所有者，并从它读取有效状态；展示需要的形态属于界面边界。持久化由有所有权的存储适配器承担。

**错误路径：** 新增 `ConfigManager`、`ConfigAdapter`、`ConfigBridge`、`ConfigCompat`，却保留全部旧验证和修改路径。命名变多了，职责问题却没变。

**另一种正确情况：** 产品要求服务停止时仍可离线编辑配置文件，那就定义服务如何加载、验证该文件。不要为了所谓“只有一个 API”强迫 CLI 必须连接正在运行的服务。

## 从决定中编写 Spec

写清实现者真正需要的内容：

- 所需能力和可观察行为，以及有意义的失败路径。
- 领域实体、字段、身份、不变条件和状态修改所有权。
- 接口、调用流程、生命周期、持久化及必要的事件顺序。
- 与实际系统后果有关的失败和恢复方式。
- 当前确实存在的公开兼容、权限和运维约束。
- 已定组件之间的契约，以及仍会影响实现的重要待决事项。

在能消除歧义的地方给出 Schema、伪代码、交互示例或时序。把开放问题放在对应实现位置。废弃的方案与历史理由若需保存，可放在设计讨论中；实现 Spec 应以已经选择的契约为主。

## 返回项目目标

新发现改变目标架构时，同时更新相关所有者和接口。只影响某个辅助函数语法时，解决该细节后继续大设计。架构任务以连贯的系统形态与可用的实现指导结束。
