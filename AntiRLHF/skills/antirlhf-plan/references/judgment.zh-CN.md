# 选择技术方向

需要在几个真实可行的方案之间作决定时，使用本文。最终给出选定行动、决定性理由和接下来要做什么。

## 找到真正需要决定的事情

先读用户要的结果及当前决定，再考虑备选。如果用户问“选哪个存储所有者”，应选出所有者。如果用户问“探索根本不同的存储架构”，就先深入调查设计空间。

识别能够区分方案的条件：谁能修改数据、消费者是否在系统外部、状态需要保存多久、延迟和性能要求、既定开发方向、选择错误后有多难修改。围绕这些差异比较方案。仅仅更换库名称的多个实现，通常属于同一路线。

## 根据错误的后果决定调查深度

对于尚未投产且容易重新修改的内部决定，选出合理方案后直接实施。例如重命名内部函数、替换无用适配器、重建测试结构，通常比维持一套过渡层更省事。

对于持久数据格式、真实用户数据删除、公开接口、安全权限和生产发布，调查真正影响迁移的事实，并把现实约束写进方案。高风险要求调查相关部分，而不是把所有普通选择都推迟。

### 完整情境：替换内部 API

**任务：** 一项旧内部 API 已被语义更完整的新接口取代，旧接口还有三个仓库内调用方。用户允许破坏内部兼容。

**首先调查：** 查找三个调用点及公开集成表面，检查真实对外契约、生成的客户端、外部消费者和持久化数据。使用仓库当前信息，不开展无限制的假想客户排查。

**仅内部调用时：** 把三个调用方迁到新接口，同次修改删除旧 API、适配器及其专属测试，写清选定的新契约，然后实现。

**存在真实外部客户端时：** 确定已承诺支持的版本与迁移要求。在公开边界维持需要的兼容期，内部仍统一为一个实现。

**错误路径：** 以“以防万一”为由留下弃用别名、双套测试和将来移除计划。原本不存在的义务因此变成长期负担。

两种情况下，真正决定差异的是现实中的外部契约。内部都应只有一套清晰实现。

## 让不确定性影响具体决定

未知事实需要通过可能造成的后果才能改变方案。说明缺什么事实、哪些动作取决于它、怎样得到该事实。如果合理取值下选择都一样，就立刻决定。

例如：“已批准的单进程服务采用进程内队列。如果架构调整为多个独立 Worker，在该部署前改选共享队列。”未来条件关联着实际架构方向，此刻无需启动三套队列基准测试。

真正的取舍值得比较；表格能帮助理解时就使用。一个方案明显满足约束时直接选择，不为了凑数量捏造第三个选项。

## 纠正时直接改变决定

用户提供此前遗漏的事实时，纳入决定。例如上游版本检查是**每次新 Session 开始**执行一次，就按这个真实频率评估成本和用户价值。如果一次请求能够便宜地通知更新，并在更新前征求用户同意，就保留功能。直接替换此前错误的建议。

若用户追问之前为什么判断错误，描述能够观察到的错误前提及其影响。Agent 通常无法观察自己生成过程的内部原因，应依据可观察事实作说明与修正。
