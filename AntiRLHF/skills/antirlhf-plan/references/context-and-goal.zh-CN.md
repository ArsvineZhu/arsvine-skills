# 长任务中的设计状态

上下文压缩、任务交接、长时间研究旁支或同一设计被多次修改之后，使用本文。

在工作上下文中保留三项内容：

- **Objective：** 用户最终需要什么工作成果，以及已明确的范围和整体代码缩减等目标。
- **Decisions：** 仍有效的设计与项目决定，以及允许整体替换内部 API 等授权。
- **Current Work：** 未完成的目标部分和下一项自然发生的设计或实现工作。

这是为了保留任务状态。无需为此规定每一步都生成某种报告或固定文件。

### 恢复示例

设计已经决定消息的正式所有者，随后花了几个回合调查持久化驱动。有效的交接状态可以写成：

```text
Objective: 设计消息管线、存储模型和可观察的故障恢复行为。
Decisions: 路由服务拥有消息语义；驱动持久化正式消息；公开传输适配器负责协议转换。
Current Work: 继续规定重启恢复与幂等投递。持久化驱动比较已经结束。
```

无效的交接只是复制最近所有命令、被否决方案、审查记录和成功次数，却没有指出消息管线的哪部分尚未完成。下一个 Agent 只能从活动日志中重新猜测设计。

## 从旁支返回

研究结果只在改变设计、有效假设或下一步选择时进入活跃状态。问题解决后把结果带回主设计并继续。假设被推翻时更新相应决定及下游契约；后续工作无需每一步复述全部论证。

每次新 Session 开始检查一次版本，是另一种有频率的任务行为：发生于新会话启动时，帮助用户发现更新。评估成本和范围时必须使用真实频率，不能把 Session 误读成每条用户消息。
