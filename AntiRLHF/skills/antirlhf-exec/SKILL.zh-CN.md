# 仓库执行

完成用户授权的仓库任务时，遵守当前生效的 AntiRLHF 宪章。选择修改前读取当前项目指令和相关实现。

## 恢复任务，而非回放操作日志

明确用户希望任务结束时什么能够正常工作；识别已经确定的设计、仍有效的要求及下一项未完成工作。大范围修改前查看工作树，保留无关的用户修改。跨模块的功能沿真实入口和消费者追踪；涉及注册或动态发现的系统，也要找到这些消费者。

对于所有者明确的局部修改，直接修改该实现。对于缺失的功能，完成用户或调用者实际使用它的整条路径。对于已获授权的结构重构，读取 `refactoring` Skill，一并修改受影响的所有者。

## 完成实现

1. 找到当前行为及其数据的所有者，沿实际路径观察足够的代码。
2. 实施选定的行为或结构修改。契约改变时，一并迁移受影响的调用方、配置、脚本、测试和有效文档。
3. 运行与改动有关的检查或真实使用路径。失败结果用于选择下一次修改；局部检查通过后继续完成剩余功能。
4. 删除用完的临时诊断代码和被替换的机制，完成用户要求的全部能力。

如果打算新增适配器、回退、重复状态或额外验证，先看真正的原因。问题属于数据模型或责任所有者时，直接修正该处；确实承担外部契约或独立职责的边界则保留。成熟库能更简单地承担通用机制时，可用它替换自制实现。

## 测试应保护实际行为

局部修复优先使用相关现有测试；确实存在独立、可能复发的遗漏时增加回归测试。大范围架构替换时，从新结构应提供的行为和有意义的失败模式重建测试；从旧套件迁入有价值的场景，同时删除废弃测试组及其夹具、辅助工具。涉及集成时，运行真实用户或系统路径。

如果用户要求精简代码或复杂度，把生产代码、测试、脚本、适配器和工作流机制一起看。发现新结构把刚删除的负担换了个名字带回来，就继续简化该结构。

## 保持任务原有的权限与约束

执行当前用户决策及适用的项目要求。局部纠正只修改对应内容，不得自动升级成全局规范。任务期间的约束在真正影响操作时持续生效：维护仓库时要求保护现有凭据，后续涉及凭据的命令同样要遵守；一个毫不相关的编译失败则无须另作“凭据未受影响”的报告。

调试、上下文压缩和分支开发之后，仍然记住未完成的要求。区分真实阻塞与猜测的未来问题；真正阻止交付时向用户指出。

## 读取实际需要的工作指导

以下路径均相对于**当前 Skill 目录**：

- `references/trajectory.md`：当前工作状态、原有用户修改、任务范围或长任务漂移。
- `references/debugging.md`：实际故障、间歇性问题、反复打补丁或调查越扩越大。
- `references/testing-and-verification.md`：测试选择、CI 结果、回归覆盖和局部变更的验证。
- `references/git-and-delivery.md`：分支、PR、集成和交付；用户指定不同操作时遵守用户要求。
- `references/examples.md`：小修复、集成、重构、测试和局部纠正的完整执行案例。

重大结构重设计或整体测试替换时，读取 `../refactoring/SKILL.md` 及相关参考。写作或编辑文档（包括 Agent 指令）时，读取 `../documentation/SKILL.md` 及相关参考。四份 Skill 作为一组安装后仍能通过这些相邻目录路径访问。

## 交付

完成所需功能，简述有效能力和重要结构变化，报告真正有用的检查结果及需要用户处理的阻塞。任务完成即结束。
