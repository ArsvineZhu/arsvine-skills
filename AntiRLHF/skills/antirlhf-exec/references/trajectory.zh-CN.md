# 让实现始终围绕实际任务

开始仓库工作、上下文压缩后恢复、接手已有工作树，或者决定旁支问题是否属于本次任务时使用本文。

## 从项目真实现状开始

读取用户希望实现的行为与明确约束、仓库现行指令，以及当前负责该行为的代码。大改动前查看 Git 状态，明确用户已有的未提交内容。区分现行源码、历史文档与 Agent 的旧提案；保留用户修改及无关文件。

长任务可在工作上下文中保留：

```text
Objective: 通过管理 API 和 CLI 实现运行中的配置更新。
Decisions: 配置服务拥有修改权；调用方使用同一种领域表示。
Current Work: API 路径已完成；CLI 仍在修改旧数据结构。
              迁移 CLI 写入、删除旧转换器，运行 CLI -> API 使用路径。
```

这是供 Agent 继续工作的状态，存在当前上下文、既有交接文件或用户指定的文档里即可。无需每执行一步都另建状态报告。

## 判断发现的问题是否属于当前任务

旁支问题如果阻碍所需行为、与本次缺陷有同一结构根因、破坏本次改动影响到的契约，或用户明确追加要求，就纳入当前修改并处理。

旧测试夹具中的独立错误，不必自动把解析器开发升级成全仓数据清洗。可以在有意义时简短提及，然后完成解析器。如果该问题实际出现在用户路径上，就应调查并修复对应所有者。

### 情境：保护登录状态，但不反复报告

**用户要求：** 仓库维护期间保留当前登录状态。

**执行过程：** 判断命令是否可能修改凭据、配置目录、Token、浏览器 Session 或保存它们的服务。避免删除或替换这些状态。后续相关操作仍须遵守。

**发生无关的 lint 失败后：** 修复 lint 或继续原任务。lint 与认证状态无关时，不再额外检测或声明“登录未受影响”。

**如果必要操作会清空凭据：** 修改执行方式，或在动手前就该动作取得明确授权。此时登录约束真正改变了行动。

一项约束有作用范围和有效期。只在那个范围内持续应用，无须变成以后所有回答的主题。

## 从旁支回到主线

调试结束后确定修复了什么、目标还缺什么、下一次实际编辑是什么。日志和旧猜测可以留在 Git 或现有材料中供需要时查阅，但不能取代任务状态。

全部所需行为可用、相关检查完成后交付。后来想到的无关优化，只有在用户授权的新任务中再做。
