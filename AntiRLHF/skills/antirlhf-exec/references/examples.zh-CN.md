# 执行案例：选定做法并完成

选择与当前工作相近的情境。先比较事实，再将做法用于不同仓库。

## 单测通过，但真正入口失败

**任务：** 添加 API 端点，保存用户配置，并使其在重启后仍有效。

**现状：** 验证函数单测通过；新端点返回成功，但 CLI 仍在写旧配置文件，重启会加载旧数据。

**错误路径：** 报告验证测试全绿；为每个 Helper 加独立测试；再造文件监听器兼容两套数据来源。

**正确工作：**

1. 追踪 Endpoint -> 配置所有者 -> 持久化 -> 重启 -> 有效状态，也追踪 CLI 写入到对应所有者。
2. 选择唯一的修改和持久化契约，让 Endpoint 与 CLI 使用它。只有产品真的需要离线文件入口时才定义对应边界。
3. 删除旧重复写入路径和转换器，按当前契约修改测试。
4. 分别运行 API -> restart -> read、CLI -> restart -> read；两条用户路径正常后结束。

**另一种证据：** 如果离线修改配置是明确功能，应将它设计成受相同验证权威控制的导入/加载操作。

## 大功能中途发现一个小故障

**任务：** 完成新解析器并通过 CLI 提供功能。

**观察：** 一个旧夹具由于 Metadata 含有错误字节而失败，它来自不再使用的预生产实验。

**错误路径：** 审查每个旧夹具，写兼容解析器和迁移命令，把 CLI 功能搁置。

**正确工作：** 确认该夹具处于当前支持路径之外，继续完成解析器和 CLI。用户确实需要知道时简短说明该旧夹具问题。

**另一种情况：** 如果该输入是真实支持的生产数据，就应按契约修正解析器或迁移数据。这时故障属于当前功能。

## 大重构制造出更大的新系统

**任务：** 统一某业务实体的三种内部表示，减少总代码和维护工作，同时保持现有能力。

**现状：** 旧转换器删除了，却出现新通用框架、每个消费者两个适配器、事件路由器以及大量测试。新系统比旧系统更大。

**错误路径：** 因为已经投入很多工作就保留新框架，继续改命名、重用测试 Helper，解释为什么代码增长合理。

**正确工作：**

1. 找出正式数据所有者为什么仍不能提供消费者真正需要的表示。
2. 把业务转换和策略移到该所有者；真实外部边界处才保留协议转换。
3. 简化消费者调用，删除新造的多余适配器、重复路由与废弃测试。
4. 从实际操作与独立故障重建测试，运行用户路径，对照用户明确的简化目标查看最终总代码与复杂度。

**另一种情况：** 多种公开协议的语义及生命周期确实独立时，保留各自适配器，让共享领域层更简单。

## 旧测试让过时架构死而不僵

**任务：** 替换一个被三个仓库内模块调用的内部 API，没有外部兼容义务。

**错误路径：** 新增弃用别名，为二十项旧测试保留包装器，再造双套资格验证矩阵。

**正确工作：** 将三个调用方迁到新接口；有价值的测试场景转移到新所有者；删除旧 API、Mock、专用夹具和重复测试，最后运行调用者真实路径。

**另一种情况：** 若有仍在支持期内的真实外部客户端，就在对外边界保留明确的兼容协议，内部仍采用统一实现。

## 文档纠正变成永久警告

**任务：** 修正用户指南的菜名，同时在无关维护工作中保护已登录状态。

**错误路径：** 把菜名写成“番茄炒鸡蛋（没有牛肉）”，给 `AGENTS.md` 添加“永远不要提牛肉”，后续每次 Lint 又主动报告登录未受影响。

**正确工作：** 在指南中直接写正确菜名，不留下错误版本。涉及凭据/Session 的命令遵守保留登录的要求，继续原维护任务。

**另一种情况：** Release 的已知问题记录可以说明以前的错误及修复时间，历史应放在发布记录而不是当前菜单后面。
