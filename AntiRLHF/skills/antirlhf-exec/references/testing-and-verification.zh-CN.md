# 保护实际行为的验证

局部功能、调试、测试选择和 CI 结果分析使用本文。大规模结构替换时整体重建测试，应读取 `../../refactoring/SKILL.md` 及其 `../../refactoring/references/testing-and-reduction.md`，此路径从当前 references 目录指向相邻 Skill。

## 为正在修改的行为选择检查

先看用户希望真正起作用的操作。优先使用能发现该操作故障的现有测试或命令。只有针对独立回归、关键边界、复杂算法或能独立失效的契约，才补充有价值的测试。

测试的价值取决于能发现什么错误、未来能保护什么行为。测试数量、断言数量和覆盖率是观察信息，本身不是任务目标。

### 情境：一个序列化修复，有六层测试可以加

**修改：** 某个可选字段的持久化形态错误。

**现有测试：** 集成测试已经涵盖 create -> persist -> restart -> read；序列化器也有专用单测。

**有效修改：** 如果字段特有缺陷可在序列化器复现，就在该测试中补充回归。若公开契约要求重启后该字段保持，则更新已有重启集成测试。运行受影响的两处检查。

**无效修改：** 在服务、Repository、Client 等六层分别添加对同一个字段的重复断言，再造专用工厂和 CI 验证矩阵。覆盖面看似变广，实际可能反复验证同一契约。

**另一种情况：** 加密、事务恢复、客户端解码可能独立失败，分别保留对应测试是有意义的。

## 让检查结果改变工作

检查失败是实际观察到的缺陷；找到所有者修复，再运行相应检查。大套件发现一个具体问题后，先处理它，不要反复运行整个套件。

局部检查通过就结束它所覆盖的问题，继续完成剩余功能。实现和有关集成行为完成后结束任务。

单测通过但 CLI 或 API 路径失败时，修复真实路径。用户使用的是入口能力，不是单元测试数量。

## 架构改变时调整测试

依赖已废弃私有接口的测试可能因为刻意替换架构而失败。判断它保护的行为是否仍然需要；有价值的场景迁到当前契约或所有者，删除旧测试及专用夹具。为了真正公开行为可以修改生产代码，但不能仅为旧 Mock 复活私有适配器。

整体测试重置应使用 Refactoring 指南，由它指导从目标能力设计、迁移有用案例和成组删除废弃测试基础设施。

## 各种工具回答各自的问题

Lint 和类型检查发现静态问题，单测验证局部行为，集成测试验证跨组件契约，真实入口的手动或脚本运行发现接线缺失，性能要求或设计选择才需要 Benchmark。用相关工具解决问题，完成后结束。
