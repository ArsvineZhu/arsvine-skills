# 修复故障，然后继续原功能

真实测试、命令、集成或用户操作失败时使用本文。将故障追到能够修复的所有者，并回到原任务。

## 追踪已经观察到的故障

1. 记录失败操作、输入、预期与实际结果。有复现症状即可开始；只有能区分可能原因时才新增诊断手段。
2. 沿受影响的数据或控制流程找到负责该行为的组件。先看最近改动和最近相关边界，再决定是否扩大调查。
3. 选择能解释症状的修复。局部行为就在局部改；多个消费者共享同一缺陷时修正结构所有者。
4. 再运行暴露故障的操作或定向测试。修改影响共享状态、持久化、传输或安全边界时扩展到对应集成路径。
5. 删除临时诊断代码，继续尚未完成的功能。

## 区分局部错误与结构错误

**局部错误：** 序列化器处理一个可选字段有误，其所有权和数据路径正常。修正序列化器并覆盖遗漏输入。

**结构错误：** 三个服务都能修改相同的缓存失效状态，每次故障修复都在不同服务打补丁。选出修改/失效所有者，让其他调用者使用它，删除重复逻辑。添加第四个回退只会重演问题。

表面故障可以很小，结构根因却很大。实际调用路径决定修改范围。

## 情境：修改后缓存仍是旧值

**观察：** 用户通过 API 更新了记录，紧接着读取还是旧值；重启进程后读取变正确。

**实际做法：** 追踪 API 修改至持久化和缓存失效，确认修改所有者是否发出失效事件、读者是否处理。修复缺失的状态迁移。在契约要求时执行 update -> read 和 restart -> read。

**错误路径：** 给每个缓存加监控、制造通用缓存一致性审计器、增加重试读取支路，然后因为缓存单元测试通过而宣布安全。这可能保留两套竞争的读取行为。

**不同证据：** 如果数据在持久化之前就丢了，应调查提交或事务所有权，而不是强行把答案归结为缓存失效。

## 故障修复完成就回主线

修复能够解释观察到的错误，相应检查通过后，继续其他授权行为。有新证据推翻原因或发现受影响集成时可以继续调查。无关部分的探索交给另一项任务。
